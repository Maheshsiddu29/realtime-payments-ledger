# Database

PostgreSQL 16. Reference for the schema, the constraints, and how migrations
and transactions are handled.

For *why* the model looks like this, see [LEDGER_DESIGN.md](LEDGER_DESIGN.md).

## Tables

### `accounts`

A balance held in exactly one currency.

| Column          | Type          | Notes                                          |
| --------------- | ------------- | ---------------------------------------------- |
| `id`            | `UUID`        | Primary key, generated by the application.     |
| `currency`      | `VARCHAR(3)`  | ISO 4217 code, upper case.                     |
| `balance_minor` | `BIGINT`      | Minor units. Never negative, never a float.    |
| `created_at`    | `TIMESTAMPTZ` | Set by the database.                           |
| `updated_at`    | `TIMESTAMPTZ` | Maintained by a trigger, not by callers.       |

Constraints:

| Name                            | Rule                        | Why                                                |
| ------------------------------- | --------------------------- | -------------------------------------------------- |
| `accounts_currency_format`      | `currency ~ '^[A-Z]{3}$'`   | Rejects empty, padded, lower-case and malformed codes. |
| `accounts_balance_non_negative` | `balance_minor >= 0`        | Overdraft is structurally impossible, not merely discouraged. |

`VARCHAR(3)` rather than `CHAR(3)`: `CHAR` pads values to the declared width,
so `'US '` and `'USD'` would compare in surprising ways and round-trip through
Go as a padded string. The regex constraint makes the fixed width redundant
anyway.

The `accounts_set_updated_at` trigger sets `updated_at` on every update, so the
value is consistent no matter which code path did the writing.

### `transfers`

The intent to move money, and its outcome.

| Column                   | Type          | Notes                                  |
| ------------------------ | ------------- | -------------------------------------- |
| `id`                     | `UUID`        | Primary key.                           |
| `source_account_id`      | `UUID`        | FK → `accounts(id)`.                   |
| `destination_account_id` | `UUID`        | FK → `accounts(id)`.                   |
| `amount_minor`           | `BIGINT`      | Always positive.                       |
| `currency`               | `VARCHAR(3)`  | Must match both accounts.              |
| `status`                 | `TEXT`        | `pending`, `completed` or `failed`.    |
| `created_at`             | `TIMESTAMPTZ` | Set by the database.                   |
| `completed_at`           | `TIMESTAMPTZ` | Set if and only if `status='completed'`. |

Constraints:

| Name                                     | Rule                                              | Why                                                     |
| ---------------------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| `transfers_amount_positive`              | `amount_minor > 0`                                | Direction comes from the account columns, not the sign. |
| `transfers_currency_format`              | `currency ~ '^[A-Z]{3}$'`                         | Same as accounts.                                        |
| `transfers_status_valid`                 | `status IN ('pending','completed','failed')`      | Closed set of states.                                    |
| `transfers_distinct_accounts`            | `source_account_id <> destination_account_id`     | A self-transfer would be a balanced pair that moves nothing. |
| `transfers_completed_at_matches_status`  | `completed_at IS NOT NULL` iff completed          | The two columns can never disagree.                     |

`status` is `TEXT` with a `CHECK` rather than an `ENUM`. Adding a state later
is then an ordinary migration instead of `ALTER TYPE`, which has awkward
transactional behaviour on older servers.

### `ledger_entries`

The actual movements. Append-only.

| Column         | Type          | Notes                                       |
| -------------- | ------------- | ------------------------------------------- |
| `id`           | `UUID`        | Primary key.                                |
| `transfer_id`  | `UUID`        | FK → `transfers(id)`.                       |
| `account_id`   | `UUID`        | FK → `accounts(id)`.                        |
| `amount_minor` | `BIGINT`      | **Signed.** Negative = debit, positive = credit. |
| `currency`     | `VARCHAR(3)`  | Must match the transfer's currency.         |
| `created_at`   | `TIMESTAMPTZ` | Set by the database.                        |

Constraints:

| Name                                  | Rule                            | Why                                                    |
| ------------------------------------- | ------------------------------- | ------------------------------------------------------ |
| `ledger_entries_amount_non_zero`      | `amount_minor <> 0`             | An entry that moves nothing is not a movement. With the balance trigger this also forces at least two entries per transfer. |
| `ledger_entries_currency_format`      | `currency ~ '^[A-Z]{3}$'`       | Same as accounts.                                       |
| `ledger_entries_one_leg_per_account`  | `UNIQUE (transfer_id, account_id)` | A transfer posts at most one entry per account, so a duplicated leg is impossible. |

## Relationships

```
accounts ──1─────< transfers          (source_account_id)
accounts ──1─────< transfers          (destination_account_id)
accounts ──1─────< ledger_entries     (account_id)
transfers ─1─────< ledger_entries     (transfer_id)   -- exactly 2 in this phase
```

## Indexes

Every index here has a query behind it. Indexes are not free: each one is
maintained on every write.

| Index                                     | Table            | Purpose                                                        |
| ----------------------------------------- | ---------------- | -------------------------------------------------------------- |
| primary keys                              | all              | Lookup by id, the dominant access pattern.                     |
| `transfers_source_account_id_idx`         | `transfers`      | Indexes the FK — PostgreSQL does **not** do this automatically — and serves per-account transfer history. |
| `transfers_destination_account_id_idx`    | `transfers`      | Same, for the other side.                                      |
| `ledger_entries_one_leg_per_account`      | `ledger_entries` | Enforces the unique constraint, and its leading `transfer_id` column serves `EntriesForTransfer`. |
| `ledger_entries_account_id_created_at_idx`| `ledger_entries` | Indexes the `account_id` FK and serves the per-account statement query ("newest entries for this account"). |

Deliberately **absent**: a standalone index on `ledger_entries(transfer_id)`.
The unique constraint above already provides a usable index led by that column,
so a separate one would be pure write overhead.

Also absent: any index on `accounts(currency)`. Nothing queries accounts by
currency, and an index without a query is a cost with no benefit.

## Triggers

| Trigger                                  | Table            | Timing                              | Effect                                                      |
| ---------------------------------------- | ---------------- | ----------------------------------- | ----------------------------------------------------------- |
| `accounts_set_updated_at`                | `accounts`       | `BEFORE UPDATE`                     | Maintains `updated_at`.                                     |
| `transfers_completed_are_immutable`      | `transfers`      | `BEFORE UPDATE OR DELETE` when completed | Rejects any change to a completed transfer.            |
| `ledger_entries_are_append_only`         | `ledger_entries` | `BEFORE UPDATE OR DELETE`           | Rejects every mutation; corrections are reversing entries.  |
| `ledger_entries_transfer_must_balance`   | `ledger_entries` | `AFTER INSERT`, **deferred**        | At `COMMIT`: the transfer's entries must sum to zero and share its currency. |
| `transfers_completed_must_balance`       | `transfers`      | `AFTER INSERT OR UPDATE`, **deferred** | At `COMMIT`: a completed transfer must have balanced entries. |

The two deferred triggers are `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY
DEFERRED`, so they run at `COMMIT` rather than per statement. This is what lets
a debit and a credit be inserted in sequence while still guaranteeing the pair
balances before anything becomes durable. See
[LEDGER_DESIGN.md](LEDGER_DESIGN.md#the-invariants-and-what-enforces-each-one)
for why a `CHECK` constraint cannot do this.

## Migrations

Managed by [golang-migrate](https://github.com/golang-migrate/migrate), applied
by `cmd/migrate`.

| Version | Migration                        | Contents                                          |
| ------- | -------------------------------- | ------------------------------------------------- |
| 1       | `create_accounts`                | `accounts`, `set_updated_at()` and its trigger.   |
| 2       | `create_transfers`               | `transfers`, FK indexes, immutability trigger.    |
| 3       | `create_ledger_entries`          | `ledger_entries`, unique constraint, append-only trigger. |
| 4       | `enforce_balanced_transfers`     | The deferred balance constraint triggers.         |

Structure (1–3) is separated from the cross-table invariant (4) so the
enforcement can be reviewed as one coherent change.

```sh
make migrate-up          # apply everything pending
make migrate-down        # roll back exactly one migration
make migrate-down-all    # roll back everything (destroys data)
make migrate-version     # print the current version
make migrate-redo        # down-all then up, proving both directions
```

Rules:

- **The application never migrates on start-up.** Several replicas booting at
  once would race to change the schema, the version would depend on which
  build started first, and a destructive operation would be hidden inside a
  routine restart. Migrations are an explicit operator step.
- **Migrations are append-only once applied beyond a local machine.** Fix a
  mistake with a new version, never by editing an applied one.
- Every migration has a matching `.down.sql`, and both directions are tested
  by `TestMigrationsRoundTrip` and by CI on every push.
- Each file wraps its statements in `BEGIN`/`COMMIT`, so a migration that fails
  partway leaves nothing behind. PostgreSQL supports transactional DDL, which
  many databases do not.
- Adding an index to a populated table needs `CREATE INDEX CONCURRENTLY`, which
  cannot run inside a transaction and therefore belongs in its own migration
  without the `BEGIN`/`COMMIT` wrapper.

## Transaction boundaries

| Operation           | Boundary                       | Isolation           |
| ------------------- | ------------------------------ | ------------------- |
| `CreateAccount`     | Single statement (implicit)    | Default             |
| `GetAccount`        | Single statement (implicit)    | Default             |
| `GetTransfer`       | Single statement (implicit)    | Default             |
| `EntriesForTransfer`| Single statement (implicit)    | Default             |
| **`PostTransfer`**  | **Explicit transaction**       | **`SERIALIZABLE`**  |

Posting is the only multi-statement operation, and it holds one transaction
across the balance reads, both balance updates, both ledger inserts, the
invariant check and the completion update. Nothing it writes is visible until
`COMMIT`, and `COMMIT` is where the deferred triggers run.

Isolation is set per transaction in Go rather than relying on a server default,
so behaviour does not depend on how a particular server was configured. The
Compose PostgreSQL is *also* configured with
`default_transaction_isolation=serializable`, which makes an interactive `psql`
session behave like the application; the CI service container is left at the
default, and the application is unaffected either way.

**Phase 1 does not retry serialization failures and does no row locking.** See
[LEDGER_DESIGN.md](LEDGER_DESIGN.md#transaction-isolation-honestly) for the
full statement of what is and is not guaranteed under concurrency.

## Connection pooling

The application uses `pgxpool`:

| Setting            | Source                       |
| ------------------ | ---------------------------- |
| `MaxConns`         | `POSTGRES_MAX_OPEN_CONNS`    |
| `MaxConnLifetime`  | `POSTGRES_CONN_MAX_LIFETIME` |
| `ConnectTimeout`   | `POSTGRES_CONNECT_TIMEOUT`   |
| `application_name` | `APP_NAME`                   |

`application_name` tags every backend in `pg_stat_activity`, so a runaway query
can be traced back to this service.

`POSTGRES_MAX_IDLE_CONNS` has **no pgxpool equivalent** — it is a
`database/sql` concept, and pgxpool controls idle connections by time
(`MaxConnIdleTime`) and floor (`MinConns`) rather than by count. Rather than
mapping it to something with different semantics, it is applied where it
genuinely belongs: `cmd/migrate`, which uses `database/sql` because that is
what golang-migrate's driver expects.

## Test databases

Integration tests never touch a development database. They use
`POSTGRES_TEST_DB` (default `ledger_test`), which the harness creates and
migrates on first run. `TestMigrationsRoundTrip` uses a second database
(`<name>_roundtrip`) so that tearing a schema down cannot disturb the other
tests.

Between tests the harness runs `TRUNCATE ledger_entries, transfers, accounts
CASCADE`. `TRUNCATE` is used rather than `DELETE` because the append-only
triggers reject `DELETE` — a real demonstration that the protection works, and
a reminder that it is row-level and does not cover table-level operations.
